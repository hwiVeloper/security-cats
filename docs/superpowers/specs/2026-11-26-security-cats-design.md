# 보안냥이 (security-cats) 설계

- 작성일: 2026-11-26
- 저장소: `github.com/hwiVeloper/security-cats` (지금은 비어 있음)
- 시안: [2026-11-26-security-cats-mockups/](2026-11-26-security-cats-mockups/) — `cats-v3.html`(고양이 가족), `home-v3.html`(홈 화면). 브라우저로 열면 보인다.
- 표시: **[결정]** 은 사용자가 정한 것, **[제안]** 은 설계자가 정한 것(사용자 확인 대상), 표시가 없으면 사실/제약.

## 1. 무엇을, 왜

보안냥이는 **보안 대응 기능을 고양이 캐릭터로 하나씩 붙여 가는 데스크톱 프로그램**이다. 보안 전문가 고양이 "보안냥이"가 본체이고, 기능마다 고양이가 한 마리씩 있다.

첫 두 마리는 지금 따로 배포되는 프로그램 두 개를 옮겨 온다.

| 고양이 | 하는 일 | 지금 프로그램 |
|---|---|---|
| 냅냥 | 안 쓰는(잠든) API 찾기: API 명세와 서버 접근 로그를 비교 | napi (이 사용자가 만듦) |
| 탐정냥 | 침해의심 IP 점검: 의심 IP가 서버 로그에 있는지, 얼마나 위험한지 판정 | iptrace (동료가 만듦) |

왜: 앞으로 보안 기능을 계속 붙일 계획이라, 기능마다 프로그램을 따로 만들고 배포하는 대신 **틀 하나**에 고양이로 붙인다. 쓰는 사람은 프로그램 하나만 받으면 되고, 서버 등록·SSH 접속 같은 공통 부분은 한 번만 만든다.

## 2. 목표 · 비목표 · 안티목표

**목표**
- [결정] 보안냥이 하나만 배포한다. 이관이 끝나면 napi.exe 와 iptrace.exe 는 배포를 멈춘다.
- [결정] 첫 배포는 **"그대로 이사"**: 두 프로그램의 기능을 빠짐없이 옮긴다. iptrace 의 AI 분석, 메일 발송, 점검 이력·검토 상태, 명령줄 실행(CLI)까지 포함.
- 새 고양이를 붙이는 비용이 작아야 한다: 새 고양이는 "무엇을 점검하고 어떻게 보여 줄지"만 만들고, 서버·SSH·설정·리포트·화면 틀은 본체 것을 쓴다.
- 화면은 napi 스타일(따뜻한 크림 바탕, 둥근 카드, 고양이 그림)로 통일한다.

**비목표 (첫 배포에서 하지 않음)**
- 새 보안 기능, 새 탐지 규칙, 판정 기준 변경. napi 의 상태 분류와 iptrace 의 등급(CRITICAL~LOW)·시그니처는 그대로.
- 고양이끼리 엮는 기능 (예: 냅냥이 찾은 "외부 탐색 시도"를 탐정냥으로 바로 점검). 나중 버전 후보.
- [제안] 어두운 테마. iptrace 에는 있지만 napi 에는 없다. 첫 배포는 밝은 테마만.

**안티목표 (돌아가도 실패로 보는 것)**
- 지금 쓰는 사람이 기능이나 데이터(설정, 점검 이력, 메모, 신뢰한 호스트 키)를 잃는 것.
- 두 프로그램 중 어느 쪽보다도 SSH 안전장치가 약해지는 것. 비밀번호를 디스크에 쓰는 것.
- 운영 서버에 지금보다 큰 부하를 주는 것.
- 이관 도중 `main` 이 깨진 상태로 남는 것 (단계마다 테스트 전부 통과).

## 3. 제약

- **실행 환경**: Windows 10/11 64비트, 폐쇄망. 관리자 권한 없이 실행. 화면은 WebView2(pywebview). Python 3.12.
- **DRM**: 대상 PC 에서 `.txt` 파일과 엑셀이 만든 xlsx/csv 는 DRM 으로 암호화된다(`<DOCUMENTSAFER` 로 시작). 프로그램이 쓰는 텍스트 파일은 `.txt` 확장자를 쓰지 않는다. PyInstaller 번들에서 `.dist-info/*.txt` 를 빼는 iptrace 방식도 유지.
- **운영 서버 보호**: 로그는 운영 WAS/WebtoB 서버에서 SSH 로 읽는다. 원본 로그를 통째로 내려받지 않고 서버에서 걸러서 필요한 줄·집계만 가져온다 (두 프로그램 모두 이미 그렇게 함).
- **배포**: 빌드한 exe 를 GitLab 릴리스에 손으로 올린다. 코드는 GitHub `hwiVeloper/security-cats`.
- **개발 환경 제약**: 개발 PC 의 작업 세션에서는 exe 와 Edge/WebView2 를 직접 띄우지 않는다(세션이 죽는다). 화면 확인은 목(mock) API 를 붙인 UI 를 일반 브라우저로 열어서 한다 (napi 의 `?mock=1` 방식). 실제 exe 확인은 사용자가 한다.
- **의존성**: 오프라인 설치용 wheelhouse 를 쓴다. 런타임 의존성은 지금 두 프로그램의 합(paramiko, pywebview, PyYAML, openpyxl 등)을 넘지 않게.

## 4. 접근 (고른 것: A)

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 단계적 이사** [결정] | 새 저장소에 napi·iptrace 를 각자 폴더로 그대로 옮긴 뒤, 본체를 새로 만들고 한 마리씩 본체로 옮긴다 | 본체를 napi 에서 떼어 설계할 수 있다. 두 프로그램의 테스트(napi 737개, iptrace 약 107개)를 안전망으로 그대로 가져간다. 단계마다 멈춰도 망가진 상태가 없다 | 옮기는 동안 옛 폴더와 새 본체가 같이 있어서 저장소가 잠시 커진다 |
| B. napi 를 키우기 | napi 패키지 이름을 바꾸고 iptrace 를 붙인다 | 가장 빠르다 | napi 전용 가정(서비스 단위 설정, 결과 저장 방식)이 본체에 남아 세 번째 고양이부터 억지로 맞추게 된다 |
| C. 새로 짜기 | 두 프로그램은 참고만 | 구조가 가장 깔끔 | 가장 오래 걸리고, 기존 테스트를 거의 못 살려 이관 버그를 잡기 어렵다 |

A 를 고른 이유: "고양이를 계속 붙인다"는 목표에 맞는 본체를 만들면서, 기존 동작을 테스트로 지킬 수 있다.

## 5. 캐릭터와 화면 [결정]

### 5.1 고양이 가족 (`cats-v3.html`)

세 마리 모두 냅냥과 같은 그림체: 같은 얼굴 모양(`HEAD_PATH`), 같은 선 굵기(4), 볼터치, `ω` 입. 구도는 **소품이 있는 전신 장면**. 작은 아이콘(40px, 24px)에서는 털색으로 구분된다.

| 고양이 | 털 | 장면 | 얼굴 |
|---|---|---|---|
| 냅냥 | 삼색이 (크림 + 주황 얼룩) | 보라 방석 위에서 낮잠, 콧방울, Zz. **지금 napi 그림 그대로** (`napi/ui/js/cat.js`) | 감은 눈 |
| 탐정냥 | 고등어 태비 (밝은 회색 + 진회색 줄무늬, 흰 입가) | 엎드려서 돋보기로 발자국을 따라감. 체크무늬 탐정 모자, 머리 위 `?` | 동그란 갈색 눈 |
| 보안냥이 | 턱시도 (검은 털 + 흰 이마줄·입가·가슴털·양말 앞발) | 파란 방패(흰 체크) 옆에 똑바로 앉아 지킴. 파란 헤드셋(마이크 포함), 연파란 받침 | **둥근 파란 눈 + 큰 동공 + 반짝이 두 개 + 수평 눈꺼풀(밝은 회색 선)**: 귀엽지만 냉철하게. 세로 동공·노란 홍채는 쓰지 않는다(무서워 보임) |

냅냥의 기존 상태별 표정(`awake`, `drowsy`, `asleep`, `rip`, `sleeptalk`, `ghost`, `probe`)은 그대로 쓴다. 탐정냥·보안냥이의 상태별 표정(진행 중, 찾음, 안전 등)은 필요한 화면을 만들 때 같은 그림체로 그린다.

### 5.2 홈 화면 (`home-v3.html`)

```
┌──────┬──────────────────────────────────────────────┐
│ [보안] │  ┌─────────────────────────────────────────┐ │
│  홈   │  │ (보안냥이 전신)  "안녕하세요, 보안냥이예요.  │ │
│ ──── │  │                  오늘 확인할 게 3건 있어요…" │ │
│ [냅냥]②│  └─────────────────────────────────────────┘ │
│ [탐정]①│  확인할 것 3건  11월 26일 · 고양이 2마리가 보고     │
│ (＋)  │  ▌[탐정] 조치 필요 · 203.0.113.7 웹쉘 경로 200   [보기] │
│ 곧합류 │  ▌[냅냥] 잠꼬대 2개 · deprecated 인데 호출됨     [보기] │
│       │   [탐정] 검토 전 2건 · 확인 완료 표시 안 함      [보기] │
│  ⚙설정 │                                               │
└──────┴──────────────────────────────────────────────┘
```

- **왼쪽 고양이 레일**: 맨 위 보안냥이(홈), 구분선, 고양이들(얼굴 아이콘 + 이름 + 숫자 배지: 빨강=조치 필요 있음, 주황=주의만), "곧 합류" 빈 자리(점선 ＋), 맨 아래 설정(⚙). 고양이를 누르면 그 기능 화면으로 들어간다. 새 고양이가 생기면 레일에 한 칸 늘어난다.
- **위쪽 요약**: 보안냥이 전신 장면 + 말풍선. 말풍선은 브리핑 목록을 한두 문장으로 요약한다(건수, 가장 급한 것).
- **확인할 것 목록** (아직 처리 안 된 것, 6절 규칙): 모든 고양이의 브리핑 항목을 급한 순(조치 필요 → 주의 → 확인)으로. 줄마다 고양이 아이콘, 한 줄 설명, 출처(고양이·대상·시각), [보기] → 그 고양이 화면의 해당 결과로 이동. 왼쪽 색 띠: 빨강/주황/없음.
- 오른쪽 고양이 패널은 **두지 않는다**.
- 확인할 것이 없으면 보안냥이가 "오늘은 확인할 게 없어요" 라고 말하고 목록 자리는 비운다.

### 5.3 고양이 화면

- **냅냥**: 지금 napi 화면을 그대로 옮긴다(서비스 목록, 요약, 상태 탭, 표, 상세, 메모, HTML/엑셀/PDF 내보내기, 스캔 진행). 왼쪽 레일 안쪽에 napi 의 서비스 목록이 그대로 들어간다.
- **탐정냥**: iptrace 의 tkinter 화면을 napi 스타일 웹 화면으로 **새로 만든다**. 화면 구성과 기능은 iptrace 와 같게: 로그 점검(IP 붙여넣기, 기간, 서버 선택, 진행, IP별 결과·근거·원본 줄·서버 상태, AI 분석, 리포트 저장, 회신 요약 복사, 메일 보내기), 점검 이력(IP 검색, 검토 상태, 메모), 대화상자(SSH 비밀번호, 호스트 키 확인, 점검 완료, AI 분석, 메일). iptrace 의 `screens/` 스크린샷이 기능 기준이다.
- **설정**: 공통(서버, 일반) + 고양이별 섹션(냅냥: 서비스·명세·로그 형식·범위, 탐정냥: 탐지 기준·로그 형식·AI·메일).

## 6. 본체와 고양이의 약속 [제안]

새 고양이를 싸게 붙이려면 본체가 고양이에게 기대하는 것을 하나로 정한다. 고양이 하나는 패키지 하나다.

- **신상**: id(영문, 예: `sleepy`, `detective`), 이름, 한 줄 설명, 얼굴 아이콘, 전신 장면 그림, 레일 순서.
- **화면**: 고양이 화면 진입점(UI 모듈)과 JS API 묶음. 본체는 레일·라우팅·공통 대화상자(비밀번호, 호스트 키, 알림)만 제공.
- **설정**: 고양이 설정 섹션과 그 저장·검증. 공통 서버 목록을 참조할 수 있다.
- **브리핑**: `briefing()` → 항목 목록. 항목 = 단계(`action` 조치 필요 / `warn` 주의 / `review` 확인), 제목, 설명, 출처(대상·시각), 이동 링크(고양이 화면 안의 위치). 본체는 모든 고양이 것을 모아 정렬하고 레일 배지와 홈 요약을 만든다. 브리핑은 저장된 최근 결과만 읽고, 서버에 접속하지 않는다.
- **데이터**: 고양이 전용 데이터 폴더(`<데이터>/cats/<id>/`). 다른 고양이 폴더는 건드리지 않는다.

**첫 브리핑 규칙** [제안]

목록은 날짜로 자르지 않는다. **"아직 처리되지 않은 것"** 을 보여 주고, 처리하면 사라진다. 그래서 화면 제목은 "확인할 것 N건"으로 한다(시안의 "오늘"은 뺀다). 처리 방법은 새로 만들지 않고 두 프로그램에 이미 있는 것을 쓴다.

- 탐정냥: 점검 이력 전체에서 검토 상태로 판단한다(기간 제한 없음).
  - 검토 상태 "조치 필요" → `action` (점검마다 한 줄).
  - "검토 전"이면서 CRITICAL/HIGH IP 가 있는 점검 → `action` (점검마다 한 줄).
  - 그 밖의 "검토 전" 점검 → `review` (건수로 묶어 한 줄).
  - 사라지게 하는 법: 점검 이력에서 검토 상태를 "확인 완료"로 바꾼다.
- 냅냥: 서비스마다 가장 최근 결과로 판단한다.
  - 잠꼬대(deprecated 인데 호출됨) 중 메모(유지 사유)가 없는 것이 있으면 → `warn` (서비스마다 한 줄).
  - 유령(명세에 없는데 호출됨)이 있으면 → `warn` (서비스마다 한 줄).
  - 결과 신뢰도 낮음(수집 실패 서버 등) → `review`.
  - 사라지게 하는 법: 다시 스캔해서 결과가 바뀌거나, 해당 API 에 유지 사유 메모를 남긴다(napi 가 이미 메모 남긴 잠든 API 를 숫자에서 빼는 것과 같은 방식). 유령은 명세 수정 후 다시 스캔.
  - 잠든 API 수는 브리핑에 넣지 않는다(고양이 화면에서 본다).

## 7. 공통 부품 [제안]

| 부품 | 기준 | 설명 |
|---|---|---|
| 서버 목록 | 새로 | 서버 하나 = 이름, 호스트, 포트, 사용자, 인증(비밀번호/키), 키 파일. 고양이는 서버를 골라 쓰고, 로그 경로·형식 같은 고양이 전용 값은 고양이 설정에 둔다. 같은 서버를 한 번만 등록. |
| SSH | iptrace 안전장치 + napi 실행 방식 | **접속 계층은 공통**: 실패한 비밀번호 재전송 금지(계정 잠김 방지), 모르는 호스트 키는 확인 대화상자 후 `known_hosts` 저장, 같은 호스트 계정 순차 접속, 동시 접속 수 제한. **실행 명령 검증은 고양이별** [제안]: 본체의 실행 함수는 "검증기"를 반드시 거쳐야만 명령을 보낼 수 있고, 검증기는 고양이가 제공한다. 탐정냥은 지금 iptrace 의 허용 목록 검증(`check_allowed`)을 그대로 쓴다. 냅냥은 셸 스크립트 형태(`sh -c '…'`, awk, 취소용 `pkill -f <토큰>`)라 허용 목록에 `sh`·`awk`를 더하면 따옴표 안이 검사되지 않아 약해지므로, 대신 **정확한 명령 검증**을 둔다: 검증된 입력(경로 glob, 형식, 기간, 토큰)으로 napi 명령 생성기를 다시 돌려 나온 문자열과 보낼 문자열이 정확히 같을 때만 통과. 두 쪽의 기존 명령 테스트(iptrace 의 `$(` 거부, napi 의 명령 문자열 비교)는 바꾸지 않는다. 서버 쪽 `timeout`/`nice`/`ionice` 는 두 고양이 모두 유지. |
| 비밀번호 | 두 프로그램 공통 | 메모리에만, 프로그램을 끄면 사라짐. 같은 `사용자@호스트:포트` 는 고양이가 달라도 한 번만 묻는다. |
| 로그 형식 | 둘 다 | napi(`logformat.py`, 자체 형식 + 프리셋)와 iptrace(Apache LogFormat 문법, WebtoB/Tomcat/JEUS 프리셋)를 하나의 형식 목록으로. 기존 두 쪽의 프리셋·사용자 정의 형식이 모두 그대로 읽혀야 한다(두 쪽 테스트가 기준). |
| 리포트 | 고양이별 유지 | 냅냥: HTML/엑셀/PDF, 탐정냥: HTML/엑셀/CSV/회신 문구/메일. 엑셀 작성기는 나중에 하나로 합쳐도 되고 안 합쳐도 된다. |
| 설정 저장 | napi 방식 | 공통 설정은 YAML. 고양이 설정은 이관 동안 원래 형식(napi YAML, iptrace JSON)을 유지해도 된다. |
| 감사 로그 | iptrace | `audit.log`(JSONL)를 데이터 폴더로. |
| 시작 기록 | napi | `napi.log` 방식의 시작 기록과 화면 로드 실패 안내를 본체로. |

## 8. 실행 파일 · 데이터 · 가져오기 [제안]

- **이름**: 저장소·exe·폴더 이름은 `security-cats`, 화면에 보이는 이름은 "보안냥이". Python 패키지는 `seccats`.
- **실행 파일**: `security-cats.exe` 한 파일(onefile, napi 처럼 로딩 화면 포함). CLI 는 `security-cats-cli.exe`(콘솔) 를 따로 만들어 같은 릴리스에 넣는다. CLI 명령과 종료 코드는 iptrace CLI 와 같게(`check`, `ioc normalize`, `doctor`, `servers test`; 0 없음 / 1 발견 / 2 오류 / 3 일부 실패).
- **데이터 위치**: `%APPDATA%\security-cats\` (napi 방식). iptrace 는 exe 옆 폴더에 저장했지만, exe 를 다운로드 폴더 등에서 실행·교체하는 경우가 많아 사용자 폴더로 모은다. [결정] iptrace 는 각자 개인 PC 에서만 쓰고 공유 폴더로 같이 쓰는 팀은 없으므로, 사람별 폴더로 충분하다(데이터 위치 변경 기능은 만들지 않는다). 시그니처 규칙 파일은 번들 버전이 더 새로우면 교체하고 옛 파일은 백업(iptrace 방식 그대로).
- **가져오기**: 처음 실행 때 `%APPDATA%\napi` 가 있으면 냅냥 설정·결과·메모·`known_hosts` 를 가져올지 묻는다. iptrace 는 데이터가 exe 옆에 있으므로 설정 화면에 "iptrace 폴더에서 가져오기"(폴더 고르기)를 두고 `config/config.json`, `config/known_hosts`, `data/history.db`, `rules/signatures.json` 을 가져온다. 원본은 건드리지 않는다(복사). DPAPI 로 암호화된 AI 키·메일 토큰은 같은 PC·같은 사용자일 때만 풀리므로, 안 풀리면 다시 입력하라고 안내한다.
- **버전**: 이관 중에는 `0.x`, 두 마리를 다 옮긴 첫 배포가 `1.0.0`.

## 9. 단계와 완료 기준 [결정: 순서 / 제안: 완료 기준]

각 단계는 별도 브랜치에서 하고, 끝나면 `main` 에 합친다. 모든 단계가 끝날 때 **두 프로그램의 기존 테스트가 전부 통과**해야 한다.

   - napi: 이력 보존 (`git subtree add --prefix=napi` 또는 `git filter-repo --to-subdirectory-filter napi` 후 병합, 방법은 빌더 선택). 추적하지 않던 것(`wheelhouse/`, `showcase/`, `.claude/`, `.superpowers/`)은 가져오지 않는다.

[결정] 기준본은 지금 `E:\workspace_claude\napi\iptrace` 에 있는 것이다. 작성자는 더 이상 고치지 않고 합치는 데 합의했으므로 다시 맞추는 단계는 없다. (참고: 코드의 `__version__` 은 1.1.0 이지만 CHANGELOG 에는 메일 기능이 든 1.2.0 이 있고, 이 기준본에는 메일 기능이 들어 있다.)
