## 0. 배경과 범위

v1.0은 **보안팀이 준 의심 IP**를 웹 접근로그에서 찾아 응답코드(404/500 등)와 공격 패턴으로 판정한다. 하지만 아래 경우는 v1.0만으로 놓칠 수 있다.

| 놓칠 수 있는 경우 | 이유 | 대응 기능 |
|---|---|---|
| 웹셸이 이미 서버에 올라가 있음 | 접근로그에는 요청만 남고, 파일 자체는 확인하지 않음 | F1 |
| 로그인 계정 탈취 | 일반 POST/200으로만 보여 공격 패턴에 안 걸림 | F2 |
| SQLi가 DB까지 도달 | 접근로그에는 500만 남고 원인(DB 오류)은 error log에 있음 | F3 |
| 데이터 대량 유출 | 정상 URL에 200이라 공격 패턴에 안 걸림 | F4 |
| 보안팀 목록에 없는 공격자 | 공격자가 IP를 바꾸거나 방화벽에 안 잡힘 | F5 |

**원칙은 v1.1과 같다**: 운영 서버는 읽기만 한다, 파일은 버튼을 눌렀을 때만 저장한다, 외부 패키지를 늘리지 않는다(표준 라이브러리 + openpyxl + paramiko).

**가장 중요한 전제: 서버 로그 원본을 PC로 내려받지 않는다.** 모든 기능은 서버 안에서 거르거나 집계한 **작은 결과만** 받도록 설계한다.
| 기능 | 서버에서 하는 일 | PC로 받는 것 |
|---|---|---|
| F1 웹셸 파일 | `find`(목록), `grep -l`(위험 코드가 있는 파일 이름만) | 파일 경로·크기·시각, 걸린 파일 이름 |
| F2 로그인 대입 | 의심 IP 줄은 이미 받음. [이상 징후 탐지]에서는 `grep -F <로그인 URL>`로 로그인 요청 줄만 | 로그인 요청 줄 |
| F3 오류 로그 | 5xx가 난 시각(초 단위 문자열)으로 `grep -F -A 50` | 그 시각 앞뒤 오류 줄 |
| F4 응답 크기 | 고정된 `awk` 프로그램으로 경로별 건수·평균·표준편차 집계 | 경로별 통계 몇 줄 |
| F5 이상 징후 | `grep -E`로 4xx·5xx·공격 키워드·스캐너 줄만 + 상한(`head -n`) / `awk`로 IP별 404·500 건수 집계 | 후보 줄(상한 있음), IP별 건수 |

## 2. F1. 웹셸 파일 점검

### 2.1 목적
웹 루트와 업로드 폴더에서 **새로 생기거나 바뀐 실행 가능한 웹 파일**(JSP 등)을 찾고, 그 안에 명령 실행 코드가 있는지 확인한다. 접근로그와 대조해 누가 그 파일을 호출했는지도 보여준다.

### 2.2 동작
1. 서버별로 설정된 `web_roots`, `upload_dirs`에서 파일 목록을 읽는다(읽기 전용).
   ```bash
   nice -n 19 ionice -c3 find <디렉터리> -xdev -type f \( -name '*.jsp' -o -name '*.jspx' -o -name '*.jspf' -o -name '*.war' -o -name '*.class' -o -name '*.sh' \) -size -5M -printf '%T@ %s %u %m %p\n'
   ```
   - `exclude_dirs`(로그, 캐시 폴더 등)는 `-path ... -prune`으로 제외한다.
   - 모든 인자는 `shlex.quote`로 감싼다.
2. 후보를 고른다.
   - **업로드 폴더 안의 실행 파일**: 시간과 상관없이 모두 후보(업로드 폴더에는 원래 JSP가 없어야 한다).
   - **웹 루트의 최근 변경 파일**: 수정 시각이 점검 기간 안인 파일.
3. 후보 파일만 내용을 검사한다(읽기 전용, 파일당 5MB 이하).
   ```bash
   nice -n 19 grep -l -I -E '<패턴>' -- <파일1> <파일2> ...
   ```
   - 한 번에 넘기는 파일 수는 100개 이하로 나눈다.
   - 패턴은 `rules/webshell_signatures.json`에 둔다. 초기 세트:

   | 분류 | 패턴 예 |
   |---|---|
   | 명령 실행 | `Runtime\.getRuntime\(\)\.exec`, `ProcessBuilder`, `cmd\.exe`, `/bin/(ba)?sh` |
   | 파라미터로 받은 명령 | `request\.getParameter\(\s*"(cmd\|exec\|command\|c)"\s*\)` |
   | 코드 숨김 | `Base64\.getDecoder`, `sun\.misc\.BASE64Decoder`, `defineClass`, `ClassLoader` |
   | 파일 조작 | `FileOutputStream`, `RandomAccessFile`, `getRealPath` |
   | 알려진 웹셸 | `JspSpy`, `Behinder`, `Godzilla`, `AntSword`, `China Chopper` 계열 문자열 |

4. 접근로그와 대조한다. 후보 파일의 URL 경로(`web_roots` 기준 상대 경로)로 기간 내 요청을 찾아 **호출한 IP, 횟수, 응답코드**를 붙인다.
5. 판정
   | 조건 | 판정 | 등급 |
   |---|---|---|
   | 업로드 폴더 안 실행 파일 + 위험 코드 있음 | 웹셸 확실 의심 | CRITICAL |
   | 위험 코드 있음 + 접근로그에 200 호출 기록 | 웹셸 사용 의심 | CRITICAL |
   | 업로드 폴더 안 실행 파일 (위험 코드 없음) | 업로드 폴더 실행 파일 | HIGH |
   | 최근 변경 + 위험 코드 있음 | 위험 코드 포함 파일 변경 | HIGH |
   | 최근 변경만 | 최근 변경 파일 (배포 여부 확인) | LOW |

   - 정상 배포로 바뀐 파일은 LOW로 많이 나온다. 설정 `deploy_allowlist`(배포 경로 패턴)에 해당하면 숨김 처리한다.
6. **기준선 비교**(선택): 점검할 때마다 후보 파일의 `경로, 크기, 수정 시각, sha256`을 이력 DB에 저장하고, 다음 점검 때 새로 생긴 파일·바뀐 해시만 따로 표시한다.

### 2.3 출력
| 열 | 내용 |
|---|---|
| 등급, 판정 | 위 표 |
| 서버, 파일 경로, 크기, 수정 시각, 소유자, 권한 | `find` 결과 |
| 걸린 패턴 | 분류명과 패턴 |
| 접근 기록 | 호출 IP 수, 총 호출 수, 응답코드 분포, 최초/최종 호출 시각 |

- 파일 내용 자체는 가져오지 않는다(증거 보존·유출 방지). 필요하면 담당자가 서버에서 직접 확인한다.
- [엑셀로 저장] 시 "웹셸 파일 점검" 시트로 저장한다.

### 2.4 주의
- 서버에 파일을 만들거나 지우지 않는다. 의심 파일을 발견해도 **삭제·격리하지 않고** 보고만 한다(증거 보존, 대응은 보안팀 절차).
- 웹 루트가 크면 `find` 부하가 생길 수 있다. 업무 시간 외 실행을 안내하고, 서버별로 순차 실행한다.

## 3. F2. 로그인 무차별 대입 탐지

### 3.1 목적
같은 IP가 로그인 URL로 짧은 시간에 반복 요청했는지, 그 뒤 로그인에 성공한 흔적이 있는지 본다.

### 3.2 동작
- 설정 `login.urls`(경로 패턴, 예: `/login.do`, `/j_spring_security_check`, `*/login*`)에 맞는 `POST` 요청을 IP별로 시간순으로 모은다.
- **시도 판정**: `login.window_minutes`(기본 5분) 안에 `login.attempt_threshold`(기본 10회) 이상 → "무차별 대입 시도" (MEDIUM)
- **성공 의심 판정**: 시도 판정 이후 같은 IP가 `login.after_login_paths`(로그인해야만 볼 수 있는 경로, 예: `/main.do`, `/mypage/*`)에 200 응답을 받음 → "로그인 성공 의심" (HIGH)
  - 접근로그에는 로그인 성공 여부가 직접 남지 않으므로 이 방식으로 추정한다. 판정 근거에 "추정"이라고 명시한다.
- 의심 IP 점검(v1.0)과 전체 로그 점검(F5) 모두에 적용한다.

### 3.3 출력
- IP별 결과의 판정 근거에 "로그인 POST 37회/5분, 이후 /main.do 200" 형식으로 표시하고 태그 `BRUTEFORCE`를 붙인다.
- 상세 로그 필터에 [로그인] 버튼을 추가한다.

## 4. F3. 오류 로그 연계

### 4.1 목적
500 응답이 났을 때 **왜** 났는지 오류 로그에서 찾아 붙인다. 특히 DB 오류가 찍혀 있으면 SQLi가 DB까지 도달했다는 강한 증거다.

### 4.2 동작
- 서버별 설정 `error_logs`에 오류 로그 경로·파일 패턴·시간 형식을 등록한다(WebtoB error log, JEUS 등 WAS 로그). 형식이 제각각이므로 **시간 추출 정규식과 시간 형식**을 설정으로 받는다.
- 결과에서 5xx 응답이 있는 요청마다, 같은 서버의 오류 로그에서 `시각 ± error_window_seconds`(기본 5초) 줄을 찾는다.
  - **서버에서 거른다**: 구간의 각 초를 오류 로그 시간 형식 문자열로 만들어(예: `[2026.09.11 03:10:05`) `zcat | grep -F -A 50 -e ... -e ...`로 그 줄과 뒤따르는 스택트레이스만 받는다. 파일당 한 번만 실행한다.
  - 여러 줄 스택트레이스는 시간이 없는 다음 줄들을 앞 줄에 붙여 한 덩어리로 읽는다(최대 50줄).
- 오류 내용에 패턴을 적용해 태그를 붙인다(`rules/error_signatures.json`).

  | 태그 | 패턴 예 | 의미 |
  |---|---|---|
  | `DB_ERROR` | `ORA-\d{5}`, `SQLSyntaxErrorException`, `You have an error in your SQL syntax`, `PSQLException`, `SQLServerException` | 입력값이 SQL에 섞여 DB 오류 발생 → SQLi가 DB까지 도달 |
  | `PATH_ERROR` | `FileNotFoundException`, `\.\./` | 경로 조작 시도가 파일 접근까지 도달 |
  | `DESERIALIZE` | `ClassNotFoundException`, `InvalidClassException`, `ObjectInputStream` | 역직렬화 공격 시도 |
  | `EXPRESSION` | `OgnlException`, `ELException`, `SpelEvaluationException` | 표현식 주입 시도 |

- 판정 반영: 공격 태그가 있는 요청이 500 + `DB_ERROR`이면 등급을 **HIGH**로 올린다(기존 MEDIUM).

### 4.3 출력
- 결과 상세에서 5xx 로그 줄을 고르면 아래에 **"관련 오류 로그"** 상자로 해당 오류 줄을 보여준다(최대 50줄, 고정폭).
- 엑셀 저장 시 상세 로그 시트에 "오류 로그" 열을 추가한다(첫 3줄 요약).

## 5. F4. 응답 크기 이상 탐지

### 5.1 목적
정상 URL이라도 의심 IP가 평소보다 훨씬 큰 응답을 받았다면 데이터 유출일 수 있다.

### 5.2 동작
- **서버에서 집계한다**: 코드에 고정된 `awk` 프로그램으로 경로별 응답 크기 통계(건수, 합, 제곱합)를 계산해 결과만 받는다. 로그 줄은 받지 않는다.
  - 경로는 정규화한다: 쿼리 제거, 숫자 ID 구간(`/board/12345` → `/board/{n}`) 치환.
  - 경로 종류가 `size.max_paths`(기본 50,000)를 넘으면 건수가 적은 경로부터 버린다.
- 의심 IP(또는 F5 후보)의 요청 중
  - 응답 크기 > 평균 + `size.sigma`(기본 3) × 표준편차 이고 `size.min_bytes`(기본 100KB) 이상 → "응답 크기 이상" (MEDIUM)
  - 기간 내 총 응답 크기가 `size.bulk_bytes`(기본 100MB) 이상 → "대량 다운로드" (HIGH)
- 표본이 `size.min_samples`(기본 30건) 미만인 경로는 판단하지 않는다.
- **서버 부하**: 서버가 모든 줄을 집계하므로 부하가 가장 크다. `nice`/`ionice`를 붙이고, 설정 `size.enabled`로 켜고 끌 수 있게 하며 기본은 끈다.

### 5.3 출력
- 판정 근거에 "평소 12KB → 4.3MB (평균의 358배)" 형식으로 표시하고 태그 `SIZE`를 붙인다.

## 6. F5. 이상 징후 탐지 (의심 IP 없이)

### 6.1 목적
보안팀 목록과 상관없이, 기간 내 로그 전체에서 **의심스러운 IP 후보**를 찾는다. 찾은 후보는 버튼 하나로 의심 IP 점검에 넘긴다.

### 6.2 동작
- 켜는 방법: [로그 점검] 탭에서 **"전체 로그의 이상 징후도 함께 탐지"** 체크박스(Codex 샘플 방식). 의심 IP 점검과 같은 기간·서버로 함께 돈다.
- **서버에서 거른다**: `zcat | grep -E <결합 패턴> | head -n <상한>`으로 후보 줄만 받는다.
  - 결합 패턴: 응답코드 4xx/5xx, `GET`이 아닌 메서드, URL 공격 키워드, 스캐너 UA, 웹셸 의심 경로.
  - 상한(`hunt.max_lines`, 기본 200,000줄)을 넘으면 "후보가 너무 많아 일부만 분석"이라고 분석 범위에 표시한다.
  - 404 건수처럼 많기 쉬운 항목은 고정 `awk` 프로그램으로 **IP별 건수만** 집계해 받는다.
- IP별로 점수를 매긴다(가중치는 설정 `hunt.weights`).

  | 항목 | 기본 가중치 |
  |---|---|
  | 공격 태그 요청 + 2xx | 50 / 건 |
  | 웹셸 의심 경로 2xx | 50 / 건 |
  | 로그인 성공 의심(F2) | 40 |
  | 공격 태그 요청 (2xx 아님) | 5 / 건 |
  | 5xx 유발 | 3 / 건 |
  | 404 | 0.2 / 건 |
  | 스캐너 UA | 10 |
  | 응답 크기 이상(F4) | 20 |

- 제외: `own_networks`, `trusted_proxies`, `hunt.allowlist`(취약점 점검 업체, 모니터링 서버 IP 등).
- 점수 상위 `hunt.top_n`(기본 50) IP를 후보로 보여준다. 등급은 v1.0 판정 규칙을 그대로 쓴다.
- 함께 보여줄 순위표: 404 많은 IP 상위 20, 500 많이 난 URL 상위 20, 공격 태그 많은 URL 상위 20, 처음 보는 `.jsp` 경로에 200 받은 요청(기간 앞 절반에는 없던 경로).

### 6.3 출력과 화면
- 결과 영역에 [의심 IP 조회] [이상 징후] 탭을 둔다(Codex 샘플 방식). [이상 징후] 표는 IP별 결과와 같은 열에 "점수" 열을 추가한다.
- 버튼
  - **[선택 IP로 의심 IP 점검]**: 고른 IP들을 의심 IP 입력칸에 넣는다.
  - **[보안팀 공유용 목록 복사]**: "IP, 점수, 판정 근거"를 탭 구분 텍스트로 복사한다(엑셀에 바로 붙여넣기 가능).

|---|---|---|

## 부록 A. 도구 밖에서 함께 볼 것 (수작업 체크리스트)

도구가 다루지 않는 부분이다. 웹 로그에서 침해 의심이 나오면 아래도 같이 확인한다.

- [ ] **방화벽 아웃바운드 로그**: 웹서버에서 외부로 나간 연결이 있는지(특히 침해 의심 시각 이후). 리버스쉘·C2 통신의 흔적이다.
- [ ] **WAF/IPS 로그**: 같은 IP·시각에 차단된 공격과 통과된 공격 구분.
- [ ] **서버 프로세스·접속 상태**: 웹 서버 계정으로 실행 중인 낯선 프로세스(`ps`), 외부로 열린 연결(`netstat`/`ss`). 서버 담당자에게 요청.
- [ ] **계정·권한 변경**: 서버 계정 추가, `crontab` 변경, `authorized_keys` 변경 여부. 서버 담당자에게 요청.
- [ ] **DB 접근 기록**: SQLi 성공 의심 시 DB 감사 로그에서 같은 시각의 대량 조회 여부.
- [ ] **증거 보존**: 의심 파일·로그는 지우거나 고치지 말고 보안팀 절차에 따라 보존한다.
